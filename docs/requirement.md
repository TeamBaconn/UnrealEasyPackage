# UnrealEasyPackage - Requirements (MVP)

> Main doc: [../CLAUDE.md](../CLAUDE.md) · Screens & flow: [user-experience.md](user-experience.md) · Data: [data-storage.md](data-storage.md) · Build commands: [build-commands.md](build-commands.md) · Directory reference: [build-footprint.md](build-footprint.md)

Scope: Windows-first, one Unreal project + one engine at a time. Cross-platform structure kept, but only Win64 packaging is required for MVP. (Refined after the UX pass - see [user-experience.md](user-experience.md).)

## R1 - Build settings (templates + profiles)
> Which parameters to expose vs. auto-manage/hide, and how each profile field maps to a `BuildCookRun` flag, is worked out in [build-commands.md](build-commands.md#5-what-to-expose-vs-auto-manage-vs-hide).

- **Templates (global, project-agnostic):** reusable base settings stored in app data - platform, config, per-phase config, default output base dir, and the output **folder-name template**. Ship a **set of fixed built-ins** (e.g. *Development*, *Shipping*) that are **undeletable and read-only** - the seed clone bases, **self-healed** (restored on launch so they can never go missing). Users add their own templates by **saving a profile as a template** (the profile row's **⋯ → Make this a template**); there is **no separate Templates manager** and **no blank/empty template.**
- **Profiles (project-local):** the concrete build config for a project. Create **only by cloning** - a chosen template (fields pre-filled) or **an existing profile** - then set the **project-specific** fields - `target` and `maps`. **There is no blank/empty profile** (the "create empty" path is removed). **Clone** any profile into a new self-contained copy - new id, `<name> (copy)`, no live link to its source. Managed in the Build Settings window (left list + **Add** (clone a template/profile) + a per-profile **⋯ menu** - *Make this a template* / *Clone* / *Delete* - right form, **Save/Discard** with an unsaved-changes guard). Self-contained - editing a template or the source profile later does not change existing profiles.
- **Phase-structured editor:** the profile form is organized by pipeline phase - **Build · Cook · Stage · Pak · Archive · Copy Extras · Clean-up** - each a collapsible **island** showing its config and an **enable toggle** (the user edits config, never raw commands; **no resolved command is shown on this screen**). **Every phase is toggleable, enabled by default** - the user can turn any off (skip Build to reuse binaries with `-skipbuild`, skip Cook to reuse a cook with `-skipcook`, etc.). The one dependency: **Pak and Archive run inside the staged tree, so they require Stage** - both are greyed off (with a clear "needs Stage" hint) when Stage is disabled. Copy Extras / Clean-up default off. Two phases are **app-owned** (not UAT): **Copy Extras** (a list of project-relative → build-relative file/folder copies into the final build, e.g. `steam_appid.txt → .`) and **Clean-up** (post-build footprint reclaim by category, on success by default). Each external phase (Build/Cook/Stage/Pak/Archive) also has an **Additional args** escape hatch appended to that phase's command - and since **Stage/Pak/Archive run as one process, their three additional-args strings merge into that single command**; `-noP4` is a default-on toggle. Phases come from an **extensible registry**, so more can be added later. Mapping + rules: [build-commands.md](build-commands.md#5-what-to-expose-vs-auto-manage-vs-hide).
- **Output destination (set in the Archive phase):** when Archive runs (the default), the build is copied to an output path, so a base dir is required. **Local or direct paths both work** - an absolute path (`C:\Builds`) is used as-is; a path **inside the project** is stored **relative** (`./Build`; the Browse picker defaults to the project root) so a committed profile resolves on any teammate's machine. Base directory + a **folder name** template with placeholders, tokens `{project} {platform} {config} {profile} {target} {date} {time}` (surfaced in an ⓘ hint; rendered lowercase; `{date}` = `YYYYMMDD`), e.g. `{project}-{platform}-{config}-{date}` → `sampleproject-windows-development-20260603`. On Run, if the resolved folder already exists, **prompt to confirm replace**.
- Profiles persist as JSON, one file per profile under `.uep/profiles/` (committed so the team shares them); templates persist in the application folder. See [data-storage.md](data-storage.md).
- Run any profile on demand; the resolved per-phase command(s) are surfaced in the **Build Logs** as the build runs (the profile editor shows **no command preview**).

## R2 - Project & environment detection
- **Open project - two requirements, both must hold:** **(1)** the **game project is valid** - the selected `.uproject` exists and parses; and **(2)** a **valid engine** is resolved - an engine folder that exists and is a real Unreal Engine root (see *Engine validity*). **Open is enabled only when both pass.** If either is **stale or invalid**, the user must replace it first (re-select / **Locate…** the engine; restore the `.uproject`) before the project can open.
- **Recent projects:** quick-access list; each entry's **project** and **engine** validity is re-checked when shown (Ready when both pass, else Invalid). Invalid entries are **kept and flagged** - the offending part (project descriptor or engine path) shows a **fix** affordance (re-locate), and a per-row **⋯ menu** offers *open project folder / open engine folder / remove*. Entries are removed only by an explicit **Remove**, never silently.
- **Engine path - saved first, auto-resolve only as fallback:** resolve the engine root in this order: **(1)** the **saved engine path** for this project's `EngineAssociation`, if it still exists and is valid; **(2)** only if that is empty/invalid, **auto-resolve** from the `.uproject`'s `EngineAssociation` - Windows registry (`HKCU\…\Epic Games\Unreal Engine\Builds` by GUID for source builds; `HKLM\…\EpicGames\Unreal Engine\<ver>` for launcher installs), macOS/Linux `Install.ini` `[Installations]`; **(3)** if auto-resolve fails, the user **selects the engine folder manually**. A manually selected (or successfully auto-resolved) engine path is **saved**, keyed by `EngineAssociation`, for future validation - so the user need not relocate every open.
- **Engine validity:** a folder is a valid Unreal Engine root iff `<root>/Engine/Build/Build.version` exists and parses (its `MajorVersion`/`MinorVersion` give the version); `Engine/Binaries/<Platform>/UnrealEditor*` and `Engine/Build/BatchFiles/RunUAT*` corroborate it.
- **Targets:** read from `Source/*.Target.cs` (target type resolved through the C# base class).
- **Project type:** detect C++ vs Blueprint-only (a `Source/` with `*.Target.cs` / C++ modules ⇒ C++). Informational only - it does **not** gate the build phase: `-build` is **always on** (a cheap no-op up-to-date check when binaries are current; a real compile only when something changed or a config was never built). Detection just informs the UI/expected timing.
- **Maps:** scan `Content/**/*.umap`, plus the `GameDefaultMap` / `EditorStartupMap` defaults from `Config/DefaultEngine.ini`.
- **Plugins:** list enabled plugins from `.uproject`.
- **Caching policy:** project **contents** - targets, project type, maps, plugins - are **never cached**: re-detected **fresh on every open** (cheap, avoids stale results), held in memory. The **engine path is the one persisted exception** - saved per `EngineAssociation` (a slow-to-rediscover, user-locatable setting) and **re-validated on every use**; auto-resolution is only the fallback when no valid saved path exists.

## R3 - Footprint management
- Scan and **categorize every build-generated path** by the step that created it (rules in [build-footprint.md](build-footprint.md)); group into **Save / Binaries / Intermediate / Cache** buckets, each node with size (GB) and location(s).
- **Selective cleanup:** tick individual category nodes and remove only those - deletion is **by category node**. (Profile-awareness applies to the automatic post-build **Clean-up phase** below; the interactive Clean tab is category-based, not profile-driven.)
- **Full cleanup:** remove **all** build-generated artifacts regardless of settings.
- **Post-build Clean-up phase:** the same categorization powers an optional **Clean-up phase** in the build pipeline (see [R4](#r4--build-process--logs) / [build-commands.md](build-commands.md#8-phase-decomposition-separate-processes-parallelism-and-timing)) that reclaims chosen categories automatically when a build finishes - on success by default, so a failed build keeps its artifacts for debugging.
- Before deleting, show what will be removed and space reclaimed; user confirms; source dirs are never offered.
- Cover the game target's + per-plugin `Binaries`/`Intermediate`, the pipeline outputs under `Saved/` (`StagedBuilds`, `Cooked`, `Shaders`, `ShaderDebugInfo`), and the project-local `DerivedDataCache`. (`Build/` output, the rest of `Saved/`, the shared/global DDC, and IDE folders like `.vs`/`.idea` are deliberately **out of scope** - see [build-footprint.md](build-footprint.md).)

## R4 - Build process & logs
- Spawn UAT `BuildCookRun` from a profile and **stream live console output** (rendering any ANSI it emits) in the Build Logs window, with progress/status and **Cancel**.
- **Phase-aware run & timing (separate-process pipeline):** execute the pipeline as discrete, separately-timed phases - **Build · Cook · Stage · Pak · Archive · Copy Extras · Clean-up** - each run independently (MVP: separate processes, Jenkins-style), overlapping **Build (game target) ∥ Cook** where the engine allows, recording each phase's start-offset, duration, and status. Phases come from an **extensible registry**; executor, graph, editor, and timing all derive from it. Feasibility, the DAG, and the executor design: [build-commands.md](build-commands.md#8-phase-decomposition-separate-processes-parallelism-and-timing).
- **Live pipeline graph:** render the run as a **dynamic Jenkins-style stage graph** - one node per phase with status (pending/running/success/failed/skipped) + elapsed time, parallel branches for concurrent phases - generated from the registry (not hardcoded), and replayable for past builds from the stored per-phase timing.
- Read **past builds'** saved logs in the same window.
- **Filter** logs to show only errors, only warnings, or all.
- **Severity classification:** tag each line error / warning / info by **parsing the line text** (not color) - anchor on the first Unreal `Category: Verbosity:` token (so an `Error` word inside a `Warning:` message isn't misread), plus compiler diagnostics (`error C####:` / `warning C####:` / `LNK`) and UAT `ERROR:`/`WARNING:` prefixes; ignore summary lines. Classifier is a pure Rust function in `runner/`, tested against real logs where it pays (e.g. SampleProject's `Saved/Logs`).
- **Status** (success/failed/cancelled) comes from the process **exit code**, not from scanning logs.
- **OS notification** on success/failure; optional sound (respects R6 preference). (The tray icon is a *minimize-to-tray* affordance for keeping a build running when the main window is closed mid-build - not a finish alert.)

## R5 - Build history & metrics
- Persist a **lean, self-contained record per build** in `.uep/history/<buildId>/` (`metadata.json` + co-located `build.log`): start timestamp, duration (total + per-phase, one entry per executed pipeline phase), **build size**, output path + modified-date, **warning/error counts**, the resolved per-phase command, and **auto-derived tags**. No profile snapshot, no per-build footprint size. Tags are **flat values** (e.g. `Win64`, `Development`, `SampleProjectSteam`, `Success`) and are the *only* categorical store; platform/config/target/status are recovered by **reverse-mapping tags** against a shared vocabulary (generation and reversal must stay consistent - one Rust module, `history/`).
- **Write timing:** the record is committed only when a build ends (success/failed/cancelled) - `history/` never holds in-progress builds; the live log streams to a scratch file (crash-safe) and is folded in on completion.
- **History index:** a derived **SQLite** DB (`.uep/cache/history.db`, normalized into `builds` + `tags` + `build_tags` + `build_phases`) powers fast filter/sort and Dashboard graphs; a **light check on launch** - history subfolder **count** vs index row count - detects drift and **prompts** to reconcile (heavy). See [data-storage.md](data-storage.md).
- **History list** (on Build): filter by tags (platform / config / target / status); delete single, selected, or all entries.
- **Open build location:** jump to a build's output folder after a **modified-date check** that confirms the folder still holds that exact build; warn if changed or missing.
- **Dashboard graphs:** compare builds over time - size, duration (with a per-phase breakdown across the pipeline phases), status - grouped by tag dimensions (platform / config / target).

## R6 - App settings
- A lightweight **settings dialog** (a modal), openable from the Project Selection gate or the Main window.
- Contains: **theme**, **notification preference** (build-finish toast/sound), and the app **version** (about).
- Persisted locally and applied globally.

## R7 - Plugin packaging (`RunUAT BuildPlugin`)
> Mechanics, the `-rocket` flag, dependency resolution, and the FAB strip rule are worked out in [build-commands.md](build-commands.md#9-plugin-packaging-runuat-buildplugin).

- **Open a plugin, not just a project:** the gate accepts a `.uplugin` as well as a `.uproject`. **Open** is a two-item menu (Project / Plugin); recents list both, with a plugin entry marked by a small neutral **Plugin** tag next to its name (projects are untagged) - replacing the project-only Ready/Invalid status column. A plugin opens with **no engine resolution** - a plugin packages **standalone** (it does not need a host `.uproject`; UAT compiles it against a chosen engine), so the compile engine is chosen per-package instead.
- **Plugin shell:** opening a `.uplugin` lands on a plugin screen that reuses the project shell's sidebar+main layout but exposes a single **Tools** tab (no Dashboard/Build/Clean - those are project concerns) holding a **collapsible Package Plugin island** (the Package button collapses with it). The streaming log opens in a **separate Plugin Log window** (same live `uep://run-*` stream, severity tint, All/Warnings/Errors filter, resolved-command island, and Cancel as Build Logs - but **no pipeline graph** and **no history**). Closing it **while the process runs stops it** (a "Discard this process?" confirm; keep the window open to keep it running); once finished/failed it closes freely.
- **Package Plugin action:** runs `RunUAT BuildPlugin -plugin=<.uplugin> -package=<dir> -rocket`. Parameters:
  - **Output folder** - the user-picked base directory the package is written under.
  - **Folder name** - a token template (`{plugin} {version} {engine} {date} {time}`), **case-preserving** (a plugin's distributable folder is conventionally its own PascalCase name), default `{plugin}-{version}`. The package dir is `base / rendered`; if it already exists it is **cleared first** (BuildPlugin copies over the top and never wipes).
  - **Unreal Engine** - a picker of engines to compile with: **enumerate** the machine's registered engines (`HKCU\…\Builds` source GUIDs + `HKLM\…\EpicGames\Unreal Engine\<ver>` launcher installs), each **validated** (real `Build.version`); plus **Browse…** to add any custom engine folder, **remembered per-plugin** (see below). A remembered engine that is **no longer valid** is dropped from the list. The `.uplugin`'s `EngineVersion` pre-selects a matching engine.
  - **Delete Binaries + Intermediate after packaging** - a checkbox (default on): removes `<package>/Binaries` and `<package>/Intermediate` on success. **Required for FAB submission** - the uploaded plugin must carry no compiled output.
- **Per-plugin machine-local settings (not committed):** the browsed engines, the output folder, and the folder-name template are remembered in one plain JSON beside the `.uplugin` - `<plugin_root>/.uap/settings.json` (its own `.uap/` folder, separate from the engine's `.uep/` convention, git-ignored, **not** in the host project root) - so re-opening the plugin recalls them without leaking a machine path into anything committed. See [data-storage.md](data-storage.md).

## Non-functional
- Build logic lives in **Rust** (`src-tauri/src/`) behind thin Tauri commands; the webview is a thin UI. Test the tricky pure logic (arg builder, log classifier, tag round-trip) with `cargo test` - pragmatic, not blanket.
- Read-only against the user's project except for explicit, confirmed cleanup actions.
- Long scans/builds must never block the UI (async task / child process).
- Persistence (see [data-storage.md](data-storage.md)): templates + settings + recents (projects **and** plugins) in the application folder (JSON); profiles in `.uep/profiles/` (JSON, committed); build records + logs in `.uep/history/` (JSON/text); derived history index in `.uep/cache/history.db` (SQLite); a plugin's Actions settings (remembered engines + output folder + folder name) in `<plugin_root>/.uap/settings.json` (git-ignored).
